## はじめに
WordPressで運営していたブログを、Astro + Cloudflare Pagesに移行した。移行完了後、ブログ記事の編集を快適にするためのデスクトップアプリケーション「Fokus Editor」の開発に着手した。この記事では、開発中に直面した課題とその解決策、そして苦労したポイントをまとめる。

---

## 開発の経緯
移行作業に着手した当初、開発に使用したCarsor上でブログ記事の更新も同時に行う想定でいたのだが、開発と執筆が同じツールだとなかなかテンションが上がらない。また、Wordpressのリッチなエディターに慣れていたため、どうしても機能や見た目の点で劣ってしまう。

そこで、これまでも愛用していた「iA Writer」などの外部エディタも検討したのだが、Astroで用いるファイル形式がMDXファイルであるため、Frontmatter（メタデータ）もファイル内に記載する必要がある。メタデータをそのまま表示すると、ソースコードを直接弄っている感覚が強く、執筆の体験としてはいまいち。また、記法も厳密であるため、編集の過程でフォーマットが崩れてしまうことも多々ある。

これらの、MDXファイルを編集する際の不満点を解決すること、かつデプロイまで一括で行えることを目標に、「**Cursor + Composer 1**」をMDXエディタの制作に着手。直近にもブログ移行作業やアプリ開発を行っており、手応えを感じていたため、移行作業と同時並行で開発を進めることにした。AI駆動の並行開発は初である。

当初の想定通り、かなりスムーズに作業を進めることができた。結果的に約半日程度で実用できるレベルまで形にできた。自分用のツールということもあり細かな要件は明確であったため、手間のかかる要件定義をスムーズに進めることができたのが要因。

開発にかかった時間は短いものの、AI駆動開発ならではの問題や障害も多く発生した。

## Phase 0: 企画・要件定義

### 背景と課題

Astroブログの記事を書く際、MDXファイルの編集には以下の課題がありました：

- **Frontmatter（メタデータ）の手入力が面倒** - YAML形式で正確に書く必要がある
- **プレビューの確認が煩雑** - `npm run dev`でサーバーを立ち上げる必要がある
- **Git操作が別途必要** - エディタとターミナルを行き来する

### 技術選定の議論

| 選択肢 | メリット | デメリット |
|:--|:--|:--|
| 案A: PyQt6（Python GUI） | Python一本で完結、開発が速い | UIが古臭くなりがち |
| 案B: Tauri + React | モダンなUI、高パフォーマンス | 技術スタックが増える |

**決定理由**: UI品質とユーザー体験を重視し、**案B（Tauri + React + FastAPI）**を採用。
ブログと同じデザインシステムを使えるため、ブランドの一貫性も保てる。

## Phase 1: MVP開発

### 目標

「記事を作成・編集・保存できる」最小限の機能を実装

### 1.1 プロジェクトセットアップ

```bash

npm create tauri-app@latest fokus-mdx-editor
```

| 技術 | 役割 |
|:--|:--|
| Tauri | Rustベースの軽量デスクトップフレームワーク（Electronより軽量） |
| FastAPI | Python製の高速APIサーバー（バックエンド処理用） |

### 1.2 記事管理機能

| 機能 | 説明 |
|:--|:--|
| ファイル一覧表示 | サイドバーにMDXファイルをリスト表示 |
| 読み込み | MDXファイルをFrontmatterと本文に分離 |
| 保存 | 編集内容をMDXファイルに書き戻し |

### 1.3 エディタ機能（Monaco Editor）
エディタの選定については、以下の基準をもとに検討を行った。
- 必要な機能が搭載されている、または実現可能であること
- 実装難易度が低いこと
- 

**Monaco Editor**はVSCodeと同じエディタエンジンで、以下を実現：

| 機能 | 説明 |
|:--|:--|
| シンタックスハイライト | Markdown記法の色分け |
| 自動補完 | タグ入力時の候補表示 |
| ショートカットキー | iA Writer準拠のキーバインド |

### 1.4 Frontmatterエディタ

GUIフォームで以下を編集可能に：

| フィールド | 型 | 必須 |
|:--|:--|:--|
| title | string | ✓ |
| pubDatetime | datetime | ✓ |
| description | string | ✓ |
| tags | string[] | - |
| draft | boolean | - |
| featured | boolean | - |

## Phase 2: Git連携機能

### 目標

「エディタ内でGit操作を完結できる」

### 実装した機能

| 機能 | 説明 |
|:--|:--|
| 変更ファイル検出 | 未保存・未コミットの状態を視覚化 |
| コミットUI | メッセージ入力フォーム |
| プッシュ | ワンクリックでリモートに反映 |
| 自動メッセージ生成 | 変更ファイル一覧を自動挿入 |

### コミットメッセージの自動生成例

```
新しい記事を追加

変更ファイル:
- src/data/blog/new-article.mdx (追加)
- src/data/blog/existing-article.mdx (変更)
```

これにより、何を変更したかがコミット履歴から一目でわかるようになりました。

### 3.3 バグ修正

#### Monaco Editor読み込み問題

| 項目 | 内容 |
|:--|:--|
| 症状 | 本番ビルドでエディタが「Loading...」のまま止まる |
| 原因 | Monaco EditorがCDNから読み込もうとするが、CSPでブロック |
| 解決策 | ローカルバンドルからロードするよう設定 |

```typescript
import { loader } from '@monaco-editor/react';
import * as monaco from 'monaco-editor';
loader.config({ monaco });
```

#### pubDatetime未来日時問題

| 項目 | 内容 |
|:--|:--|
| 症状 | 日本時間12:00入力 → UTCで21:00（翌日）で保存される |
| 原因 | タイムゾーン変換のロジックが逆 |
| 解決策 | FrontmatterEditorでローカル時間→UTC変換を正しく実装 |

## 💡 学んだこと

1. **静的サイトの利点と課題**: ビルド時に全てが確定するため、動的な処理には工夫が必要
2. **CDNの重要性**: 画像配信はCDN経由が圧倒的に速い
3. **ネームサーバー変更は待ちが必要**: 即座に反映されないことを理解しておく
4. **シークレット管理の重要性**: `.env`ファイルは絶対にコミットしない
